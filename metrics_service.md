# metrics-service

Patterns, conventions, and gotchas specific to `ansible/metrics-service`.

### Prometheus metrics endpoint secured behind IsSystemAdminOrAuditor
- **Repo**: ansible/metrics-service
- **Commits**: adde11d (#251)
- **What happened**: The `django_prometheus` metrics endpoint was moved from the unauthenticated `/metrics` path to `/api/metrics` and wrapped in a `PrometheusMetricsView` (AnsibleBaseView subclass) with `permission_classes = [IsSystemAdminOrAuditor]`. A temporary 302 redirect from `/metrics` to `/api/metrics` maintains backwards compatibility for existing Prometheus scrapers during rollout. The nginx location block was also updated. An OpenAPI schema generation script (`tools/generate-openapi.sh`) was added to handle known cross-platform schema differences (macOS vs CI Linux) via deterministic patches.
- **Insight**: django-prometheus's default `ExportToDjangoView` is unauthenticated and leaks operational data (request rates, DB stats, error rates). Always wrap it in a permission-gated view. The backwards-compat redirect (302, not 301) lets scraper configs be updated gradually without data loss.

### Dashboard collection enabled by default with simplified flag management
- **Repo**: ansible/metrics-service
- **Commits**: 13ad18b (#275)
- **What happened**: The `DASHBOARD_COLLECTION` feature flag was promoted from opt-in (default False) to default-on by adding it to the `FEATURE` dict in `defaults.py`. The YAML-based AAPFlag seeding machinery (`feature_flags.yaml`, `load_task_feature_flags`, `sync_flag_values_from_settings`, `post_migrate` signal handler) was deleted entirely (-560 lines). The `metrics_service` management command's `--skip-feature-flag-init` argument was also removed. Opt-out remains available via env var, installer attribute, or Gateway UI toggle.
- **Insight**: Feature flag infrastructure should match the current lifecycle stage. Pre-GA opt-in flags need complex seeding machinery; post-GA default-on flags just need a dict entry with env var override. Deleting 560 lines of flag management code when the flag becomes default-on is a significant simplification.

### Platform auditor access via RBAC property + DAB bypass action flags
- **Repo**: ansible/metrics-service
- **Commits**: c99bfe5 (#302)
- **What happened**: System auditors were getting 401 on dashboard collection_status because DAB's `has_super_permission(user, 'view')` requires `ANSIBLE_BASE_BYPASS_ACTION_FLAGS = {"view": "is_platform_auditor"}` to be configured. The gateway conveys auditor status via JWT `global_roles`, not `user_data`, so no user flag was set. A `User.is_platform_auditor` property was added that queries RBAC assignments for the "Platform Auditor" `RoleDefinition` (no migration needed). The settings change mirrors `aap_gateway_api/defaults.py`.
- **Insight**: Each AAP service must explicitly configure `ANSIBLE_BASE_BYPASS_ACTION_FLAGS` to match the gateway's configuration. Without this, `IsSystemAdminOrAuditor` only checks `is_superuser` (via `BYPASS_SUPERUSER_FLAGS`) and never grants auditor access. The property-based approach on the User model integrates with DAB's `getattr(user, flag_name)` pattern without requiring a database migration.

### APIConfig.service_type must match gateway ServiceType.name
- **Repo**: ansible/metrics-service
- **Commits**: 110d01e (#313)
- **What happened**: `APIConfig.service_type` was set to `"metrics_service"` but the gateway's `ServiceType` table has `name="metrics"`. This mismatch caused `migrate_service_data` to skip metrics-service during install, leaving `ServiceCluster.service_id = None`. When a user's JWT claims hash mismatches (new users, permission changes), metrics-service calls `/api/gateway/v1/jwt_claims/` with a service JWT using its own UUID as the `iss` claim. The gateway validates by looking up `ServiceCluster(service_id=iss)`, which failed because `service_id` was never populated, resulting in 403s on `collection_status` and other endpoints.
- **Insight**: The `service_type` value in a service's resource API config must exactly match the `name` column in the gateway's `ServiceType` table -- a mismatch silently prevents service registration, and the failure only surfaces later when JWT claims refresh is needed.

### Prometheus metrics endpoint moved to versioned URL path
- **Repo**: ansible/metrics-service
- **Commits**: b9f9eb2 (#318)
- **What happened**: The `PrometheusMetricsView` was registered at `api/metrics`, but `ServicePrefixMiddleware` strips `/api/metrics` from incoming requests and prepends `/api` before Django routing. This caused the endpoint to only be reachable via the double-path `/api/metrics/metrics` externally, while `/api/metrics/v1/metrics` returned 404. Moved to `api/v1/metrics` (external: `/api/metrics/v1/metrics`), consistent with all other versioned endpoints. Added a permanent 301 redirect from `api/metrics` for backwards compatibility.
- **Insight**: Services behind the AAP gateway's `ServicePrefixMiddleware` must register endpoints under `api/v1/` (not directly under `api/`) because the middleware strips the service-level prefix before routing -- endpoints at `api/<name>` become unreachable or require double-path access.

### Dashboard retention from Controller cleanup schedule (now opt-in)
- **Repo**: ansible/metrics-service
- **Commits**: 112f12e (#319), 10eb8bf (#340)
- **What happened**: Dashboard collection previously used a static `DASHBOARD_COLLECTION['INITIAL_BACKFILL_DAYS']` setting for the retention window. PR #319 replaced it with `get_retention_days()`, which queries the AWX `main_systemjobtemplate` + `main_schedule` tables for active `cleanup_jobs` schedules and uses the most aggressive (lowest) `retention_days` value. Only enabled schedules with valid integer `retention_days` are considered. Falls back to 90 days if the query fails. The `database` kwarg was also renamed from `"database"` to `"awx_database"` with backwards-compat deprecation warning via `_get_renamed_kwarg()`. **PR #340 then gated `get_retention_days()` behind `DASHBOARD_COLLECTION['USE_CONTROLLER_RETENTION']` (default False)** because the function was not fully tested across all deployment scenarios. Both initial backfill and daily cleanup now use the fixed 90-day `DEFAULT_RETENTION_DAYS` by default. Opt-in via `METRICS_SERVICE_DASHBOARD_COLLECTION__USE_CONTROLLER_RETENTION=true`.
- **Insight**: The dynamic retention approach is sound in principle but was shipped before full validation. Gating behind an opt-in flag with a safe static default is the right pattern when a dynamically-derived setting reads from another service's DB and hasn't been tested in all environments.

### Dashboard pipeline fixes: NaT handling, task ordering, one-shot preservation, watermark alignment
- **Repo**: ansible/metrics-service
- **Commits**: aca0683 (#314), 4c810bc (#333)
- **What happened**: Multiple dashboard pipeline fixes across two PRs. (1) PR #314 added `_STRING_FIELDS` to `_serialize_dashboard_record` -- nullable string columns (`organization_name`, `project_name`, `launched_by_username`, `label_ids`) arrive as `float('nan')` from pandas when the entire column is null, and `DjangoJSONEncoder` serialised them as the invalid JSON token `NaN`, causing the `post_collect_hook` to silently fail. (2) PR #333 fixed four issues: `_parse_dt` now handles pandas null serialised as the string `"NaT"` (previously crashed `datetime.fromisoformat`); added telemetry recording to `sync_dashboard_host_summaries` (was missing vs `sync_dashboard_job_records`); swapped task ordering so `hourly_unified_jobs` (XX:05) fires before `hourly_job_host_summary` (XX:10) because the host summary sync looks up `JobData` rows created by the job sync; and added one-shot task preservation in `create_system_tasks()` that snapshots completed one-shot tasks before deletion and restores their status after recreation, preventing upgrades from re-running already-completed init tasks (e.g. `initial_dashboard_collection`). (3) PR #333 also aligned the watermark to use `last_finished_timestamp()` instead of `last_timestamp()` so the `since` watermark matches the `finished` index used by all dashboard collection queries.
- **Insight**: The task ordering bug (host summaries running before job records exist) is a data dependency that isn't expressed in the cron schedule -- the 5-minute stagger is sufficient but only correct when the tasks are ordered properly. The one-shot preservation pattern (snapshot completed status, delete all, recreate, restore) is a general solution for systems that delete-and-recreate system tasks on upgrade.

### Job label sync with key-absent vs key-null distinction
- **Repo**: ansible/metrics-service
- **Commits**: d73d931 (#306)
- **What happened**: The dashboard job sync pipeline gained label support: labels are parsed from the `label_ids` column in collected data and synced via `_sync_labels`. A `label_ids` field was added to `ReportSerializer` and injected into report list responses via a batched post-pagination query. The critical fix distinguishes between key-absent (`"label_ids" not in row`, older collector versions -- preserve existing labels) and key-present-but-null (`row["label_ids"] is None` -- clear stale label records). The `_inject_label_ids` method runs a single `JobLabel` query scoped to `base_qs` (same filters as the report), excludes null `label_id` values, and injects `label_ids: [int]` into each aggregated row without inflating aggregates.
- **Insight**: Data pipeline sync functions must handle schema evolution gracefully. When a new column may be absent in data from older upstream versions, treat absence as "no information" (preserve existing state) rather than "empty" (delete existing state). This requires explicit `key not in dict` checks rather than relying on `dict.get(key)` which collapses both cases into `None`.

### Dashboard card counts computed from raw job queryset, not aggregated queryset
- **Repo**: ansible/metrics-service
- **Commits**: 17a3cd12 (#386)
- **What happened**: `DashboardReportViewSet.details()` derived total_runs/total_successful_runs/total_failed_runs from `_build_aggregated_queryset()`, which filters out any `JobData` row with `template_metadata_id=NULL` (needed for cost/time annotations that depend on TemplateMetadata fields). Orphan jobs (no template metadata) still appeared in the raw job listing, causing the summary cards and the listing to disagree on totals (AAP-85129). The fix computes card counts directly on `filtered_qs` using `Count("id", filter=Q(status=...))`, keeping the `template_metadata_id` filter only for the cost/time aggregate that actually needs it.
- **Insight**: When a queryset applies filters needed by some aggregations but not others, split the aggregation into separate queries -- one for counts on the full population, one for cost/time calculations on the filtered subset. Mixing them in a single aggregate causes silent undercounting of the broader metric.

### Workflow child jobs excluded from hourly dashboard sync hook
- **Repo**: ansible/metrics-service
- **Commits**: f2822d33 (#388)
- **What happened**: The `_build_dashboard_sync_hook` filter in `collect_hourly_metrics.py` only excluded `launch_type='sync'` from dashboard job ingestion. Workflow child jobs (`launch_type='workflow'`) have `launched_by_id=NULL`, so they inflated Successful/Failed card counts without appearing in the Top 5 Users chart (which groups by `launched_by_id`). The batch collector in metrics-utility was already fixed (see [metrics_collection.md](metrics_collection.md#dashboard-jobs-collector-excludes-workflow-child-jobs-alongside-sync-jobs), m-u #525), but the hourly incremental sync hook is an independent data path with its own filter. The fix changed `raw_data["launch_type"] != "sync"` to `~raw_data["launch_type"].isin(["sync", "workflow"])`.
- **Insight**: When two independent data paths write to the same table (batch collector and hourly sync hook), both must apply identical exclusion criteria. A fix in one path does not automatically apply to the other -- each filter must be updated separately.

### Dashboard label disambiguation by organization instead of dedup
- **Repo**: ansible/metrics-service
- **Commits**: d3ce5e63 (#389)
- **What happened**: AWX labels are organization-scoped (`unique_together = (name, organization)`), so identically named labels across orgs are distinct rows with different IDs. The initial fix (#387) used `GROUP BY name / MIN(id)` to collapse them, which was incorrect -- it lost legitimate per-org labels (see [bugs_and_pitfalls.md](bugs_and_pitfalls.md#awx-label-dedup-via-group-by-collapsed-org-scoped-labels----reverted-next-day) for the fix-revert-replace arc). The replacement (#389) joins `main_organization` and appends the organization name only to labels whose name occurs more than once across the full result set (e.g., "production (Org A)", "production (Org B)"). Unique names are left unchanged. Duplicate detection runs against the complete matching dataset (ignoring LIMIT/OFFSET) so that a name split across pages is still disambiguated consistently. A separate `_fetch_duplicate_label_names()` query computes the duplicate set using `GROUP BY name HAVING COUNT(*) > 1`.
- **Insight**: When entity names are scoped by a parent (org-scoped labels, team-scoped projects), deduplication by name destroys legitimate data. Instead, disambiguate by appending the scope identifier only when there is ambiguity. The duplicate detection must use the full unfiltered/unpaginated dataset to ensure consistent disambiguation across paginated responses.

### Per-domain architecture docs added under docs/ with Mermaid diagrams (and stale-reference corrections)
- **Repo**: ansible/metrics-service
- **Commits**: 3fd25af8 (#398)
- **What happened**: A set of per-domain architecture docs was added under `docs/` (with Mermaid diagrams) covering core/RBAC, the task system, APScheduler scheduling, collectors, settings, dashboard API/sync, anonymization, and data models, cross-linked from README and CLAUDE.md and out to the dispatcherd repo. Beyond the new docs, the PR corrected several stale references that had drifted from the current code: `TaskChain` (removed model), signals-based task submission (no longer used), the `init-system-tasks` command name, and the `DASHBOARD_COLLECTION` default. It also renamed "task-group toggles" to "feature enablement settings" and drew an explicit distinction between `METRICS_COLLECTION`-style enablement settings and platform feature flags (DAB `AAPFlag` and the `feature_flags_service` collector data). The collectors schedule diagram was switched from a Mermaid `gantt` to a `flowchart` timeline because bare `:15`-style times are invalid under gantt `dateFormat HH:mm` and don't render on GitHub. Review follow-ups clarified enablement precedence, dashboard/metrics coupling, the AWX scheduling gate, and dynamic-settings override behavior.
- **Insight**: Documentation-only PRs are still worth reviewing against code because they surface accumulated drift — this one caught references to a removed model (`TaskChain`), a superseded submission mechanism (signals), a renamed command, and a wrong default. Two reusable gotchas: keep the enablement-setting vs platform-feature-flag distinction explicit (they are different mechanisms), and GitHub's Mermaid gantt requires full `dateFormat`-conformant times — use a flowchart for a bare schedule timeline.
