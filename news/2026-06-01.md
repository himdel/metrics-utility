## Weekly Metrics Repos Report (May 26 – May 29, 2026)

### metrics-utility (1 commit merged)

- **Mock Segment server for integration testing** (ansible/metrics-utility#409) — A Go-based mock Segment HTTP server was added under `tools/mock-segment-server/` for end-to-end testing of the Segment shipping pipeline. The existing `test_from_gather_to_json.py` integration test now sends the computed anonymized rollup to the mock server and validates that all chunked track events arrive with correct metadata. `StorageSegment` gained a `host` setting for mock redirection. CI was updated with a Go build step. Initially prototyped in Python, switched to Go for reliability.

### metrics-service (7 commits merged)

- **Bump metrics-utility dep to >=0.8.0** (ansible/metrics-service#229) — Ensures only the salt-free metrics-utility version is accepted, matching the service-side removal of `salt` in #215.
- **Comprehensive OpenAPI specification** (ansible/metrics-service#196) — All REST endpoints now have `drf-spectacular` `@extend_schema` decorators. Generated YAML/JSON specs (~24k lines) are committed and validated in CI. A new `sync-openapi-specs.yml` workflow auto-publishes changes to `ansible-automation-platform/aap-openapi-specs` on every push to devel. Notable: this re-introduces `drf-spectacular` which was removed in #73.
- **Dashboard performance benchmarks** (ansible/metrics-service#224) — New `benchmark_dashboard/` directory with two scripts: API latency benchmarks and collection throughput benchmarks (backfill + incremental sync), plus a data generator and documentation.
- **Fix subscription cost calculation** (ansible/metrics-service#214) — `cost_per_second()` was dividing monthly cost by 86400 (seconds/day), distributing cost uniformly regardless of actual job activity. Rewritten to weight by actual elapsed seconds: `period_cost / sum(elapsed_seconds_in_period)`. Multi-month ranges now prorate correctly.
- **Merge dashboard collection into hourly collectors** (ansible/metrics-service#210) — Major architecture change. The standalone 6-hourly `daily_dashboard_collection` task was eliminated. Dashboard sync now runs as a `post_collect_hook` on the `unified_jobs` hourly collector, keeping Controller DB calls per hour unchanged at 2. Initial backfill uses cursor-paginated batches (default 5,000). Hook exceptions are swallowed so dashboard failures can't abort the anonymization pipeline. 22 squashed commits; extensive test coverage.
- **Fix dashboard_reports tests broken by batch-pagination refactor** (ansible/metrics-service#244) — Four tests still mocking `_collect_jobs` broke after #210 refactored it into `_get_job_id_range` + `_process_batches`. Fixed by patching the new sub-function.
- **Fix: Log WARNING during retries, ERROR only on final failure** (ansible/metrics-service#226) — Two `logger.error()` calls fired unconditionally on task failure, producing false alarms when retries remained. Now logs WARNING while `can_retry()` is True, ERROR only on final failure. Automated fix by Debuggernaut (claude-opus-4-6).

### Inconsistencies & Notes

- **DRF Spectacular reversal**: `drf-spectacular` was explicitly removed from metrics-service in #73 (May 2026) with the plan to use `ansible_base.api_documentation` instead. Now re-added in #196 just weeks later. The DAB documentation path appears to have been abandoned — worth confirming whether this is the settled direction.
- **`unified_jobs` vs `unified_jobs_dashboard` collector split**: metrics-service#210 swaps in `unified_jobs_dashboard` (from metrics-utility) when dashboard collection is enabled, but this creates a subtle contract: the service now depends on the library's `unified_jobs_dashboard` collector existing and producing a superset of `unified_jobs` columns. This cross-repo dependency isn't enforced by any test in the service repo.
- **AI-generated fix attribution**: ansible/metrics-service#226 was created by "Debuggernaut (claude-opus-4-6)" running autonomously, per the commit messages. This is noteworthy as a process pattern — the fix went through proper PR review, unlike the earlier DispatcherdReconnectFilter incident that was committed directly.
